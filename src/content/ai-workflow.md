2026 年的面试已经把 AI 从"加分项"变成"必考项"。但考的不是"你会不会用 ChatGPT"，而是**你是否建立了与 AI 协作的工程方法**。

## 一、日常 AI 工作流

### 分层：AI 做什么，人做什么

| 环节 | AI 的合理角色 | 人的职责 |
| --- | --- | --- |
| 需求理解 | 生成澄清问题清单 | 与产品对齐真实目标 |
| 方案设计 | 列举备选与权衡 | **做决策** |
| 编码 | 样板、补全、重构 | 审查逻辑与边界 |
| 测试 | 生成用例骨架 | 判断哪些算有效用例 |
| 调试 | 分析堆栈、提出假设 | 验证假设、定位根因 |
| 文档 | 生成初稿、翻译 | 校正准确性 |
| 评审 | 扫查常见问题 | 判断架构与业务一致性 |

核心：**AI 加速"产出"，判断与验证仍在人手上。**

### 一个真实的协作案例

> **场景**：把 800 行的表单组件拆成 composable。
>
> **AI 做了什么**：给出三套方案（按字段拆、按功能拆、按"校验/渲染"分离），并生成第一版 `useFormValidation`。
>
> **我做了什么**：
> 1. 否掉"按字段拆"—— 字段会变，拆完维护成本更高
> 2. 选"校验/渲染分离"—— 校验逻辑最独立、最可测
> 3. 补 AI 漏掉的异步校验竞态处理（`AbortController`）
> 4. 加 6 个单测覆盖边界（空值、超长、并发、取消、错误码、重置）
>
> **结果**：组件 800 → 260 行，校验逻辑从不可测变为可单测，新增字段的改动点从 4 处降到 1 处。

这种表述体现的是"我如何驾驭 AI"，而不是"AI 帮我写了代码"。

## 二、验证 AI 输出的四道关

```js
// 1. 能跑吗（最小验证）
npm run test -- <相关用例>
npm run typecheck

// 2. 边界对吗（主动补测）
// AI 最常漏：空数组、并发、取消、异常分支、超大输入

// 3. 依赖可信吗
// AI 会编造不存在的 API 或库版本 → 必须验证 import 真实存在

// 4. 与既有代码一致吗
// 一致性比"看起来更优"更重要
```

### AI 最常出的三类错误

| 类型 | 表现 | 验证手段 |
| --- | --- | --- |
| 幻觉依赖 | `import from 'some-lib'` 但包不存在 | `npm ls` / lockfile |
| 幻觉 API | 用了不存在的参数或方法 | 类型检查 + 文档 |
| 边界遗漏 | 忽略并发、取消、空值 | 补测边界用例 |

```js
// 典型：AI 生成的请求没有处理竞态
const res = await fetch(url)
setData(res.data)
// 若两个请求乱序返回，旧数据会覆盖新数据

// 正确
const controller = new AbortController()
const res = await fetch(url, { signal: controller.signal })
if (!controller.signal.aborted) setData(res.data)
```

## 三、用工具链保证质量

人会疲劳，AI 输出量大时靠逐行审查不现实。正确做法是**把质量约束前置到工具链**。

### 三层防护

```
第一层：让 AI 少犯错（输入侧）
第二层：让错误立刻暴露（工具侧）
第三层：让人聚焦判断（评审侧）
```

### 第一层：约束输入

```md
<!-- 项目内的 AI 规范文件 -->
- 使用 TypeScript strict，禁止 any
- 状态管理用 Pinia，禁止直接修改 props
- 所有异步请求必须处理 loading / error / 取消
- 新增工具函数必须有对应单测
- 禁止引入未在 package.json 中声明的依赖
```

给 AI 提供**现有代码作为参考**，输出质量会显著提升：

```md
参考 src/utils/request.ts 的封装方式，为 /api/orders 新增 getOrders。
要求：
- 复用现有 http 实例
- 返回类型定义在 src/types/order.ts
- 错误处理与现有方法一致
```

### 第二层：自动化检查（必须阻断）

| 检查 | 工具 | 是否阻断 |
| --- | --- | --- |
| 类型 | `tsc --noEmit` | ✅ |
| Lint | ESLint | ✅ |
| 单测 | Vitest / Jest | ✅ |
| **依赖真实性** | `npm ls` / lockfile diff | ✅ |
| 体积预算 | bundlesize | ✅ |
| 安全扫描 | `npm audit` | ✅ |

```yaml
- run: pnpm typecheck
- run: pnpm lint
- run: pnpm test -- --coverage
- run: pnpm build && pnpm bundlesize
```

### 第三层：评审聚焦判断

AI 生成的 PR 常常"看起来正确、风格统一、测试通过"。评审应聚焦 AI 无法判断的部分：

| 评审重点 | 具体问题 |
| --- | --- |
| 需求匹配 | 这真的解决了用户的问题吗？ |
| 边界 | 空数据、超大输入、并发、取消 |
| 可维护性 | 三个月后还能改吗？ |
| 一致性 | 与既有架构是否冲突？ |
| 隐含假设 | 代码假设了什么前提？ |

### 可直接使用的审查清单

```md
## 正确性
- [ ] 是否有对输入不做校验的地方？
- [ ] 异步是否处理了失败与取消？
- [ ] 是否有隐含的时序假设？

## 安全
- [ ] 是否把用户输入拼进 HTML / SQL / 命令？
- [ ] 是否有硬编码密钥？
- [ ] 新增依赖是否可信？

## 可维护
- [ ] 是否重复实现了现有工具函数？
- [ ] 命名是否与项目一致？

## 测试
- [ ] 关键分支是否都覆盖？
- [ ] 是否覆盖边界（空、超长、并发、异常）？
```

## 四、用 AI 重构遗留项目

### 核心原则

**重构 = 不改变外部行为的前提下改善内部结构**。所以流程必须围绕"如何证明行为没变"。

```
建安全网 → 小步重构 → 每步验证 → 持续交付
```

### 阶段一：建安全网（占 40% 时间）

```js
// 1. 为关键路径补测试（补"行为"，不补"实现"）
// 2. 建立端到端冒烟测试（覆盖核心流程）
// 3. 补充监控埋点，建立"重构前基线"
```

::: warn 不要用 AI 生成的测试当安全网
```
AI 根据现有代码生成的测试，往往"测试了现有实现"而非"测试了正确行为"
→ 如果现有代码有 bug，测试会把 bug 固化下来
```
正确做法：**先由人定义期望行为**（用业务语言），再让 AI 生成测试代码。
:::

### 阶段二：识别重构单元

```
高价值 + 低风险 → 优先做
高价值 + 高风险 → 先补测试再做
低价值 → 不做
```

| 信号 | 含义 |
| --- | --- |
| 变更频率高 | `git log` 多次修改 |
| 缺陷密度高 | 该模块 bug 多 |
| 依赖复杂 | 循环依赖、深层嵌套 |

### 阶段三：小步重构

```
第 1 步：提取工具函数（不改逻辑）
第 2 步：拆分组件（不改逻辑）
第 3 步：替换实现（改逻辑，但测试覆盖）
```

每一步都应：能独立合并、有对应测试、可回滚。

### AI 在重构中的适配度

| 任务 | 适合度 | 说明 |
| --- | --- | --- |
| 读懂旧代码并画依赖图 | ⭐⭐⭐⭐⭐ | 极强 |
| 生成等价测试骨架 | ⭐⭐⭐⭐ | 需人定义期望 |
| 机械替换（API 更名） | ⭐⭐⭐⭐⭐ | 批量可控 |
| 提取纯函数 | ⭐⭐⭐⭐ | 逻辑清晰时 |
| 拆分组件 | ⭐⭐⭐ | 需人判断边界 |
| 改架构 | ⭐⭐ | 需人主导 |
| 处理隐式副作用 | ⭐ | AI 容易漏 |

### 明确"不做什么"

```
本次重构只做：
- 拆分 order.js（1200 行 → 4 个模块）
- 提取校验逻辑为纯函数
不做：
- 不改接口协议
- 不升级框架版本
- 不改 UI
```

范围蔓延是重构最大的风险。

## 五、AI 时代的核心竞争力

### 变化的事实

| 能力 | AI 之前 | AI 之后 |
| --- | --- | --- |
| 写样板代码 | 耗时 | 几乎免费 |
| 记住 API 细节 | 有价值 | 价值大幅下降 |
| 手写常见算法 | 有区分度 | 失去区分度 |

2026 的面试已在调整：纯算法题权重下降，系统设计、工程实践、AI 运用权重上升。

### 不变的能力

| 能力 | 为什么难以替代 |
| --- | --- |
| **判断力** | AI 给 5 种方案，说不出"你这个团队该选哪个" |
| **问题定义** | "页面太慢" → "LCP 4.2s，主因 TTFB 与主图" |
| **验证兜底** | 如何证明它真的可以（测试、指标、定位） |
| **系统权衡** | 跨模块、跨时间的取舍 |
| **沟通推动** | 让五个团队接受一个方案 |

```
AI 把"实现"变廉价，
于是"决定实现什么"与"验证是否真的实现了"变昂贵。
```

### 判断 AI 输出是否可信的自检

> **如果这段代码出 bug，我能在多长时间内定位？**
>
> - < 10 分钟：我掌握了它
> - 10–30 分钟：需要看代码，但能理解
> - \> 30 分钟：**我还没真正掌握，不应该直接合并**

这条标准比任何流程都有效。

## 六、团队层面的规范

| 层面 | 措施 |
| --- | --- |
| 输入 | 项目内 AI 规范文件、提供参考代码 |
| 工具 | 自动化检查必须阻断合并 |
| 评审 | AI 代码单独标注，评审聚焦边界与架构 |
| 度量 | 跟踪缺陷密度、回滚率 |
| 合规 | 敏感数据不进 AI、生成代码做许可证检查 |

::: interview 面试视角
面试官真正在判断的是"你会不会不加验证地信任 AI"。能给出"验证四道关"、"自动化阻断"、"明确不用 AI 的场景"，比列出十个工具名有说服力。
:::
