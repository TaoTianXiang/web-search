## 核心差异

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 保证送达、有序、不重复 | 不保证 |
| 流量控制 | 有（滑动窗口） | 无 |
| 拥塞控制 | 有（慢启动、拥塞避免） | 无（QUIC 在应用层实现） |
| 头部开销 | 20 字节起 | 8 字节 |
| 传输方式 | 字节流 | 数据报（保留消息边界） |
| 广播 / 组播 | ❌ | ✅ |

## 适用场景

| 场景 | 协议 | 原因 |
| --- | --- | --- |
| 网页、API | TCP（或 QUIC） | 需要可靠有序 |
| 文件传输 | TCP | 完整性 |
| 邮件 | TCP | 完整性 |
| 视频直播 | UDP / QUIC | 宁可丢帧不要延迟 |
| 在线游戏 | UDP | 低延迟 |
| DNS 查询 | UDP（大响应转 TCP） | 一次一问，开销小 |
| 音视频通话 | UDP（WebRTC） | 实时性优先 |

## 为什么 HTTP/3 用 UDP

不是"UDP 更快"，而是**在 UDP 之上可以自定义可靠传输**，从而摆脱 TCP 的两个限制：

1. **TCP 层的队头阻塞**：一个包丢失会阻塞所有流
2. **内核实现难以快速演进**：TCP 改动需要操作系统升级，QUIC 在用户态实现，可随应用更新

```
HTTP/2 over TCP:  丢包 → 所有 stream 等待
HTTP/3 over QUIC: 丢包 → 只有该 stream 等待（流级别重传）
```

QUIC 自己实现了：可靠传输、拥塞控制、流量控制、TLS 1.3 集成、连接迁移。

## UDP 的"不可靠"不代表不能可靠

WebRTC 在 UDP 上实现了部分可靠性（关键信令走可靠通道，音视频帧允许丢失）。可靠性可以按需构建，而 TCP 的可靠性是强制的。

## 实际工程考量

```
选 TCP：需要"完整、有序、不重复"
选 UDP：需要"低延迟、可容忍丢包"，或需要自定义传输策略
```

::: tip 前端相关
- 普通 HTTP 请求：无需关心（由浏览器处理）
- WebSocket：基于 TCP
- WebRTC：基于 UDP（音视频）+ TCP（信令）
- HTTP/3：基于 QUIC（UDP）
:::

::: warn 常见误解
"UDP 比 TCP 快"不准确。在不丢包的理想网络下，两者吞吐相近。UDP 的优势是**没有握手与重传等待**，在丢包或高延迟网络下延迟更低。
:::

::: interview 面试视角
能说清"HTTP/3 用 UDP 是为了在应用层实现流级可靠传输、绕开内核 TCP 演进缓慢"，比只说"UDP 快"高一个层次。
:::
