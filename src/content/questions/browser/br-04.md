## 决策流程

```
请求资源
  ├─ 命中强缓存（未过期）→ 直接用，200 from cache
  ├─ 已过期 → 带校验头发请求
  │    ├─ 304 → 复用本地
  │    └─ 200 → 更新本地
  └─ 无缓存 → 正常请求
```

## 强缓存

| 头 | 说明 |
| --- | --- |
| `Cache-Control: max-age=N` | N 秒内直接使用 |
| `Cache-Control: immutable` | 有效期内即使刷新也不校验 |
| `Expires` | 绝对时间（HTTP/1.0，有客户端时钟问题） |

`Cache-Control` 优先级高于 `Expires`。

## 协商缓存

| 头对 | 语义 |
| --- | --- |
| `ETag` / `If-None-Match` | 内容指纹，精度高 |
| `Last-Modified` / `If-Modified-Since` | 时间戳，精度到秒 |

`ETag` 优先于 `Last-Modified`（后者在同一秒内多次修改时判断不出变化）。

## no-cache vs no-store

| 指令 | 含义 |
| --- | --- |
| `no-cache` | **可以缓存**，但每次使用前必须向服务端校验 |
| `no-store` | **完全不存储**（含内存） |
| `must-revalidate` | 过期后必须校验，不能用过期副本 |
| `private` | 只允许浏览器缓存（CDN 不缓存） |
| `public` | 允许 CDN 等共享缓存 |
| `s-maxage` | 只对共享缓存生效 |

这两者是最常被答错的一对。

## 推荐的组合策略

```http
# index.html：必须校验，保证发版即时生效
Cache-Control: no-cache

# app.[hash].js：内容不变 URL 不变
Cache-Control: public, max-age=31536000, immutable

# 接口：私有 + 必须校验
Cache-Control: private, max-age=0, must-revalidate
```

核心原则：**入口不缓存，资源永久缓存**。

## 为什么静态资源可以永久缓存

文件名带内容 hash（`app.3f2a1b.js`），内容变化则 URL 变化，浏览器视为新资源。旧文件永久缓存不会导致"用户拿到旧代码"。

```js
// webpack
output: { filename: '[name].[contenthash:8].js' }
```

::: warn 常见事故：HTML 被强缓存
```
index.html 设置了 max-age=31536000
→ 发版后用户仍加载旧的 HTML → 引用旧的 JS hash → 页面白屏或功能异常
```
HTML 必须是 `no-cache`（或 `max-age=0, must-revalidate`）。这是成本最低的保险。
:::

## CDN 的两级缓存

```
浏览器缓存 → CDN 边缘节点缓存 → 源站
```

- `s-maxage` 只对 CDN 生效
- `stale-while-revalidate`：先返回过期副本，后台更新（减少用户等待）
- 发布时刷新 CDN 的 HTML，静态资源靠 hash 自然切换

## 排查缓存问题的顺序

1. DevTools → Network → 勾选 Disable cache（开发时）
2. 看 Response Headers 的 `Cache-Control` 是否被中间层改写
3. 检查 CDN 的回源与缓存规则
4. 用 `curl -I` 直接验证服务端返回的头
5. 确认 Service Worker 是否拦截了请求（SW 优先级最高）

::: tip Vary 头的陷阱
`Vary: User-Agent` 会让缓存按 UA 分片，命中率骤降。应使用 `Vary: Accept-Encoding` 这类高基数小的字段。
:::

::: interview 面试视角
能准确区分 `no-cache` 与 `no-store`，并说出"HTML 必须 no-cache"的实战理由，就基本过关。能补充 CDN 两级缓存与 `stale-while-revalidate`，是加分项。
:::
