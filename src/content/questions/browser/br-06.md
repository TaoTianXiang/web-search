## 三次握手

```
Client                          Server
  │──── SYN (seq=x) ──────────►│  LISTEN
  │◄─── SYN+ACK (seq=y,ack=x+1)│  SYN_RCVD
  │──── ACK (ack=y+1) ────────►│  ESTABLISHED
```

**目的**：双方都确认"自己的发送能力和对方的接收能力"正常。

| 次数 | 确认内容 |
| --- | --- |
| 第 1 次 | 服务端知道：客户端发送能力正常 |
| 第 2 次 | 客户端知道：服务端收发都正常 |
| 第 3 次 | 服务端知道：客户端接收能力正常 |

为什么不是两次：两次时服务端无法确认"客户端能收到我的包"，且历史滞留在网络中的 SYN 会导致服务端建立无效连接。

```
旧连接：客户端发出 SYN，网络延迟很久才到服务端
→ 服务端以为是新连接，分配资源并回 SYN+ACK
→ 客户端已不再需要，不会回 ACK
→ 服务端白白等待（资源浪费）
```

## 四次挥手

```
Client                          Server
  │──── FIN ──────────────────►│  CLOSE_WAIT
  │◄─── ACK ───────────────────│
  │                            │（服务端处理完剩余数据）
  │◄─── FIN ───────────────────│  LAST_ACK
  │──── ACK ──────────────────►│  CLOSED
```

**为什么是四次**：TCP 是全双工，两个方向需要**独立关闭**。

服务端收到 FIN 后可能还有数据要发，所以先回 ACK（"我收到了你的关闭请求"），等自己的数据发完再发 FIN（"我也要关了"）。这中间就是 `CLOSE_WAIT` 状态。

## TIME_WAIT

主动关闭方在发出最后一个 ACK 后进入 `TIME_WAIT`，等待 2MSL（通常 60 秒）。

两个作用：

1. **保证最后一个 ACK 能到达**：若 ACK 丢失，对方会重发 FIN，此时本端还在 TIME_WAIT 可以重发 ACK
2. **防止旧连接的数据包干扰新连接**：等待足够时间让旧连接的包在网络中消亡

### 大量 TIME_WAIT 的影响

高并发短连接服务（如未开启 keep-alive）会产生大量 TIME_WAIT，占用端口资源。

```bash
# 查看
netstat -n | awk '/^tcp/ {++S[$NF]} END {for(a in S) print a, S[a]}'

# 缓解
# 1. 开启 keep-alive 复用连接
# 2. 调整内核参数（谨慎）
net.ipv4.tcp_tw_reuse = 1
```

## SYN Flood 攻击

攻击者发送大量 SYN 但不回 ACK，服务端为每个半连接分配资源，最终耗尽。

防御：SYN Cookie（不立即分配资源，把状态编码在序列号里）。

## 与 HTTP 的关系

| 场景 | 建连成本 |
| --- | --- |
| HTTP/1.1 短连接 | 每次请求 1 RTT 握手 |
| HTTP/1.1 keep-alive | 复用连接 |
| HTTP/2 | 单连接多路复用 |
| HTTP/3 | QUIC 内置握手（1-RTT / 0-RTT） |

::: tip 前端能做什么
- 使用 `preconnect` 提前建连
- 减少域名数量（减少建连次数）
- 确保开启 keep-alive（`Connection: keep-alive`）
:::

::: interview 面试视角
"三次握手是为了确认双方收发能力，四次挥手是因为全双工需要分别关闭"是标准答案。能补上"TIME_WAIT 保证最后 ACK 可达 + 防止旧包干扰"，即为完整。
:::
