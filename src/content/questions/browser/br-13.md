## 三种情况

| 属性 | 下载 | 执行时机 | 顺序保证 | 阻塞解析 |
| --- | --- | --- | --- | --- |
| 无 | 阻塞解析下载 | 下载完立即执行 | ✅ | ✅ |
| `async` | 并行下载 | 下载完立即执行（可能打断解析） | ❌ | 下载时不阻塞，执行时阻塞 |
| `defer` | 并行下载 | 解析完成后，DOMContentLoaded 之前 | ✅ | ❌ |

```html
<script src="a.js"></script>          <!-- 阻塞 -->
<script src="b.js" async></script>    <!-- 谁先下完谁先跑 -->
<script src="c.js" defer></script>    <!-- 按顺序，解析后执行 -->
```

## 时序图

```
无属性:
  [解析]──阻塞──[下载 a.js]──[执行]──[继续解析]

async:
  [解析═══════════════]
     [下载 b.js]──[执行]──（打断解析）

defer:
  [解析═══════════════]
     [下载 c.js════════]
  [解析完成]──[执行 c.js]──[DOMContentLoaded]
```

## 模块脚本的特殊行为

```html
<script type="module" src="main.js"></script>
```

`type="module"` **默认就是 defer 行为**：

- 并行下载
- 解析完成后才执行
- 保证顺序（按文档中的出现顺序）
- 自动严格模式
- 支持顶层 `await`

加 `async` 则变成"下载完立即执行"：

```html
<script type="module" async src="a.js"></script>
```

## 选择建议

| 场景 | 选择 |
| --- | --- |
| 现代前端入口（ESM） | `type="module"`（天然 defer） |
| 需要 DOM 就绪的脚本 | `defer` |
| 独立的第三方统计（无依赖） | `async` |
| 有相互依赖的库 | `defer` |
| 必须尽早执行的（polyfill、反 FOUC） | 行内脚本或同步 |

```html
<!-- 典型配置 -->
<script defer src="/polyfills.js"></script>
<script defer src="/vendor.js"></script>
<script defer src="/app.js"></script>
```

## 常见错误

```html
<!-- ❌ async 顺序不确定，依赖关系会崩 -->
<script async src="jquery.js"></script>
<script async src="plugin-needs-jquery.js"></script>

<!-- ✅ 用 defer 保证顺序 -->
<script defer src="jquery.js"></script>
<script defer src="plugin-needs-jquery.js"></script>
```

```html
<!-- ❌ 行内脚本不能用 defer -->
<script defer>console.log('x')</script>   <!-- defer 被忽略 -->

<!-- ✅ 行内脚本需要自己等待 DOM -->
<script>
  document.addEventListener('DOMContentLoaded', () => { /* ... */ })
</script>
```

## 与 preload 的区别

```html
<link rel="preload" href="/main.js" as="script">
<script defer src="/main.js"></script>
```

- `preload`：提前下载，**不执行**
- `defer`：控制执行时机

两者可以组合使用，让关键的 JS 尽早开始下载。

能说清"module 默认 defer"、"async 不保证顺序所以有依赖时必须用 defer"、"行内脚本的 defer 会被忽略"，就覆盖了所有实际踩坑点。
:::
