## 三代对比

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 传输层 | TCP | TCP | QUIC（基于 UDP） |
| 格式 | 文本 | 二进制分帧 | 二进制分帧 |
| 并发 | 每域名 6 连接 | 单连接多路复用 | 单连接多流 |
| 头部压缩 | 无 | HPACK | QPACK |
| 队头阻塞 | 应用层 | **TCP 层仍存在** | 流级别解决 |
| 建连 | TCP + TLS | TCP + TLS | QUIC 内置 TLS，1-RTT/0-RTT |

## HTTP/1.1 的问题与"优化手段"

每个域名最多 6 个并发连接，超出就排队。于是业界发明了：

- 域名分片（domain sharding）：拆成 `static1.a.com`、`static2.a.com`
- 雪碧图（CSS sprite）：合并小图标
- 资源内联（base64）
- 文件合并（concatenation）

这些手段在 HTTP/2 下**反而有害**：破坏缓存粒度、增加请求数、内联内容无法单独缓存。

## HTTP/2 的改进

1. **二进制分帧**：把请求/响应拆成帧，交错发送
2. **多路复用**：一个 TCP 连接上并行多个 stream
3. **HPACK 头部压缩**：静态表 + 动态表 + 哈夫曼编码
4. **服务端推送**（已被主流浏览器移除）

### 为什么 HTTP/2 仍有队头阻塞

多路复用解决的是**应用层**（HTTP）的队头阻塞，但底层仍是 TCP：

```
Stream A 的帧丢失 → TCP 必须重传并等待 → 所有 stream 都被阻塞
```

TCP 保证**字节流有序**，一个包丢了，后续所有包即使收到也要等它重传。这就是"TCP 层队头阻塞"，HTTP/2 无法绕过。

## HTTP/3 / QUIC

三个关键设计：

1. **基于 UDP**：在用户态实现可靠传输，不受内核 TCP 限制
2. **流级别独立**：每个 stream 有自己的序列号与重传，一个流丢包不影响其他流
3. **0-RTT / 1-RTT 建连**：QUIC 内置 TLS 1.3，首次 1-RTT，会话复用时 0-RTT
4. **连接迁移**：用 Connection ID 而非 IP+端口标识连接，切换 WiFi/4G 不断连

```
HTTP/2: 丢一个包 → 所有流等待
HTTP/3: 丢一个包 → 只有那个流等待
```

代价：UDP 在部分企业网络被封锁，需要回退到 HTTP/2。

## 实践建议

| 场景 | 建议 |
| --- | --- |
| HTTP/1.1 | 仍需域名分片、雪碧图（老项目） |
| HTTP/2 | **去掉**域名分片、雪碧图、文件合并 |
| HTTP/3 | 开启并配置回退（`Alt-Svc`） |

```http
Alt-Svc: h3=":443"; ma=86400
```

服务器通过这个响应头告知客户端"我支持 HTTP/3"，客户端下次尝试使用。

::: warn 迁移到 HTTP/2 时的常见退步
```
原来：把 20 个 JS 合并成 1 个
HTTP/2 下：1 个巨大文件无法与业务代码分离缓存，改一行就全部失效
```
应改为按业务边界拆分，让不常变的依赖独立成 chunk。
:::

::: interview 面试视角
能准确说出"HTTP/2 的队头阻塞在 TCP 层而非应用层"，并解释 QUIC 用 Connection ID 实现连接迁移，就达到了高级水平。
:::
