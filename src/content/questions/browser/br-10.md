## 规范层面的差异

| 维度 | GET | POST |
| --- | --- | --- |
| 语义 | 获取资源（安全、幂等） | 处理资源（非安全、非幂等） |
| 参数位置 | URL query | 请求体 |
| 缓存 | 可缓存 | 默认不缓存 |
| 历史记录 | 会记入 | 不记入 |
| 书签 | 可收藏 | 不可 |
| 幂等 | ✅ | ❌ |
| 可重放（如刷新页面） | 安全 | 可能重复提交 |

## 澄清几个常见误解

### "GET 有长度限制"

**HTTP 规范本身没有长度限制**。限制来自实现：

| 环节 | 限制 |
| --- | --- |
| 浏览器地址栏 | 数千字符（Chrome 约 8KB 显示，实际可更长） |
| 服务器 | Nginx 默认 `large_client_header_buffers` 约 8KB |
| 代理 / 网关 | 各自的配置 |

POST 的请求体同样有服务器限制（如 Nginx `client_max_body_size` 默认 1MB）。

### "POST 比 GET 安全"

**都不安全**。明文 HTTP 下两者都能被抓包。HTTPS 下两者都加密（URL 也会加密，但会记录在服务器访问日志里）。

真正的差异：GET 参数会出现在 URL 中，因此更容易被**日志、浏览器历史、Referer** 泄露。

### "POST 会产生两个 TCP 包"

这是旧实现的行为（先发头，再发体），现代浏览器通常合并。不是规范要求，不应作为答题依据。

## 幂等性的实际意义

```
GET /users/1        → 多次调用结果相同（幂等）
PUT /users/1        → 多次调用结果相同（幂等）
DELETE /users/1     → 多次调用结果相同（幂等）
POST /users         → 多次调用会创建多个用户（非幂等）
```

这直接影响重试策略：

```js
// ❌ 网络抖动时自动重试 POST 可能重复创建
retry(() => fetch('/api/orders', { method: 'POST', body }))

// ✅ 用幂等键（idempotency key）
fetch('/api/orders', {
  method: 'POST',
  headers: { 'Idempotency-Key': uuid() },
  body
})
```

服务端用这个 key 去重，保证重复请求只创建一次。

## 选型原则

| 场景 | 方法 |
| --- | --- |
| 查询列表、详情 | GET |
| 创建资源 | POST |
| 全量更新 | PUT |
| 部分更新 | PATCH |
| 删除 | DELETE |
| 复杂查询（参数超长） | POST（约定为查询语义） |

复杂查询用 POST 是常见妥协：参数可能超过 URL 长度，但语义上是"查询"。此时应保证服务端不产生副作用。

## 缓存的实际影响

```js
// GET 可以被 CDN / 浏览器缓存
fetch('/api/products?page=1')   // 可能命中缓存

// POST 默认不缓存，需要显式声明
fetch('/api/search', { method: 'POST', body })
```

若用 POST 做查询，需要单独设计缓存（如服务端 Redis），失去 HTTP 缓存的天然支持。
