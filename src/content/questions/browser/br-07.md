## 目标

同时做到三件事：

1. **机密性**：内容不被窃听
2. **完整性**：内容不被篡改
3. **身份认证**：确认对方是真正的服务器

## 为什么两种加密都要用

| 类型 | 优点 | 缺点 |
| --- | --- | --- |
| 对称加密（AES） | 快 | 密钥分发困难 |
| 非对称加密（RSA/ECDHE） | 密钥交换安全 | 计算慢 |

所以 HTTPS 的组合是：**用非对称加密协商出对称密钥，之后用对称加密传输数据**。

## TLS 1.3 握手（简化）

```
Client                                Server
  │── ClientHello ──────────────────►│
  │   (支持的套件、key_share)          │
  │◄── ServerHello + 证书 + key_share ─│
  │   (选定套件、服务器公钥参数)        │
  │   [双方用 ECDHE 算出相同共享密钥]   │
  │── Finished ─────────────────────►│
  │◄── Finished ─────────────────────│
  │═══ 后续用对称密钥加密通信 ════════│
```

1 个 RTT 完成。TLS 1.2 需要 2 个 RTT（且不支持 0-RTT 会话复用）。

## 数字证书的作用

证书解决的是"**我拿到的公钥是不是真的属于这个域名**"。

```
证书内容：
  域名、公钥、有效期、颁发机构
  + CA 的数字签名（用 CA 私钥对上述内容的哈希签名）
```

验证流程：

1. 浏览器用**内置的 CA 根证书公钥**验证签名
2. 验证域名是否匹配
3. 验证有效期
4. 检查是否在吊销列表（CRL / OCSP）

若都通过，说明"这个公钥确实由受信任的 CA 为该域名签发"。

## 中间人攻击如何被防

```
无证书时：
攻击者 ──伪造公钥──► 客户端
攻击者 ◄─真连接──── 服务器
（攻击者可以解密所有内容）

有证书时：
攻击者无法伪造 CA 签名 → 浏览器拒绝连接
```

攻击者的两种可能：

| 手段 | 结果 |
| --- | --- |
| 用自己的证书 | 域名不匹配 / 非受信 CA → 浏览器报错 |
| 转发真实证书 | 无法解密（没有服务器私钥） |

## 常见证书问题

| 报错 | 原因 |
| --- | --- |
| `NET::ERR_CERT_DATE_INVALID` | 证书过期 |
| `NET::ERR_CERT_COMMON_NAME_INVALID` | 域名不匹配 |
| `NET::ERR_CERT_AUTHORITY_INVALID` | 自签名或 CA 不受信 |
| 混合内容（Mixed Content） | HTTPS 页面加载了 HTTP 资源 |

```html
<!-- 混合内容会被浏览器阻止 -->
<script src="http://cdn.example.com/lib.js"></script>

<!-- 正确 -->
<script src="https://cdn.example.com/lib.js"></script>
```

## HSTS

```http
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
```

作用：告诉浏览器"以后访问我这个域名一律用 HTTPS"，即使输入的是 `http://`。

`preload` 可把域名写入浏览器内置列表，但**移除非常困难**（需要数月），上线前要慎重。

## 性能成本

| 项 | 优化 |
| --- | --- |
| 握手 RTT | TLS 1.3、0-RTT、`preconnect` |
| 证书链过大 | 减少中间证书、使用 ECDSA 证书 |
| 加解密开销 | 现代 CPU 有 AES-NI 指令，开销很小 |

::: tip 前端能做的事
1. 全站 HTTPS，避免混合内容
2. 配置 `preconnect` 到 API 域名
3. 检查第三方资源的证书有效性（否则会阻塞页面）
:::

::: interview 面试视角
能说清"非对称用于协商密钥、对称用于传输数据"、"证书解决公钥归属问题"，并解释中间人为何无法伪造，就是完整链路。
:::
