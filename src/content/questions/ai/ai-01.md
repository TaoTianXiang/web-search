## 回答框架

```
分工（哪些环节用 AI） → 工具 → 具体案例 → 验证机制 → 边界（哪些不用）
```

只罗列工具名没有价值。面试官想听的是**具体的协作方式**。

## 一个可复用的分层

| 环节 | AI 的合理角色 | 人的职责 |
| --- | --- | --- |
| 需求理解 | 生成澄清问题清单 | 与产品对齐真实目标 |
| 方案设计 | 列举备选与权衡 | **做决策** |
| 编码 | 生成样板、补全、重构 | 审查逻辑与边界 |
| 测试 | 生成用例骨架、穷举边界 | 判断哪些算有效用例 |
| 调试 | 分析堆栈、提出假设 | 验证假设、定位根因 |
| 文档 | 生成初稿、翻译 | 校正准确性、补充上下文 |
| 评审 | 初步扫查常见问题 | 判断架构与业务一致性 |

## 具体案例（示例表述）

> **场景**：把一个 800 行的表单组件拆成 composable。
>
> **AI 做了什么**：读代码后给出三套拆分方案（按字段、按功能、按校验/渲染分离），并生成第一版的 `useFormValidation`。
>
> **我做了什么**：
> 1. 否掉"按字段拆"，因为字段会变，拆完维护成本更高
> 2. 选"按校验/渲染分离"，因为校验逻辑最独立且可测
> 3. 修改 AI 生成的代码：它漏掉了异步校验的竞态处理，我补了 `AbortController`
> 4. 加了 6 个单测覆盖边界（空值、超长、并发、取消、错误码、重置）
>
> **结果**：组件从 800 行降到 260 行，校验逻辑从不可测变为可单测，新增字段的改动点从 4 处降到 1 处。

这种回答体现了：AI 加速了"产出"，但**判断与验证仍然是人做的**。

## 验证 AI 输出的四道关

```js
// 1. 能跑吗（最小验证）
npm run test -- <相关用例>
npm run typecheck

// 2. 边界对吗（主动补测）
// AI 最常漏：空数组、并发、取消、异常分支、超大输入

// 3. 依赖可信吗
// AI 会编造不存在的 API 或库版本 —— 必须验证 import 真实存在

// 4. 与既有代码风格一致吗
// 一致性比"看起来更优"更重要
```

## 工具分类（不必报品牌名，说明用途）

| 用途 | 典型形态 |
| --- | --- |
| 编辑器内补全 / 对话 | IDE 插件 |
| 大范围重构 / 多文件修改 | Agent 型工具 |
| 代码评审 | PR 自动审查 |
| 单测生成 | 测试辅助 |
| 文档 / 注释 | 生成 + 人工校正 |
| 日志 / 错误分析 | 堆栈解读 |

## 明确"不用"的场景

这比"我用很多 AI"更能体现判断力：

| 场景 | 原因 |
| --- | --- |
| 涉及密钥、用户隐私的代码 | 数据合规风险 |
| 核心算法与安全逻辑 | 需要可证明的正确性 |
| 不熟悉的新领域 | 无法判断输出对错 |
| 架构决策 | 需要理解业务约束 |

::: warn 最常见的问题：假装理解
```js
// AI 生成的代码你贴进去能跑，但说不出为什么这样写
// → 线上出问题时无法定位 → 变成技术债
```
判断标准：**如果这段代码出 bug，我能在多长时间内定位？** 超过 30 分钟，就说明我还没真正掌握它。
:::

::: interview 面试视角
面试官真正在判断的是：你会不会"不加验证地信任 AI"。能给出"验证四道关"和"明确不用 AI 的场景"，比列出十个工具名有说服力。
:::
