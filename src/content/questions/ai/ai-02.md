## 核心思路：用工具把"检查"变成自动化的

人会疲劳，AI 输出量大时靠人工逐行审查不现实。正确做法是**把质量约束前置到工具链里**。

## 三层防护

```
第一层：让 AI 少犯错（输入侧）
第二层：让错误立刻暴露（工具侧）
第三层：让人聚焦判断（评审侧）
```

### 第一层：约束输入

```md
<!-- 在项目里放 AI 规范文件（如 .github/copilot-instructions.md） -->
- 使用 TypeScript strict 模式，禁止 any
- 状态管理用 Pinia，禁止直接修改 props
- 所有异步请求必须处理 loading / error / 取消
- 新增工具函数必须有对应单测
- 禁止引入未在 package.json 中声明的依赖
```

给 AI 提供**项目上下文**（现有组件、工具函数、类型定义），输出质量会显著提升。

```md
<!-- 提示词示例 -->
参考 src/utils/request.ts 的封装方式，为 /api/orders 新增一个 getOrders 方法。
要求：
- 复用现有 http 实例
- 返回类型定义在 src/types/order.ts
- 错误处理与现有方法一致
```

### 第二层：自动化检查（必须阻断）

| 检查 | 工具 | 是否阻断 |
| --- | --- | --- |
| 类型 | `tsc --noEmit` | ✅ |
| Lint | ESLint（含并发/未清理等规则） | ✅ |
| 单测 | Vitest / Jest | ✅ |
| 依赖真实性 | `npm ls` / lockfile diff | ✅ |
| 体积预算 | bundlesize | ✅ |
| 安全扫描 | `npm audit` / Snyk | ✅ |
| 重复代码 | jscpd | 警告 |

```yaml
# CI 关键：任何一项失败不允许合并
- run: pnpm typecheck
- run: pnpm lint
- run: pnpm test -- --coverage
- run: pnpm build && pnpm bundlesize
```

### 第三层：评审聚焦判断

AI 生成的 PR 常常"看起来正确、风格统一、测试通过"。此时评审应聚焦 AI 无法判断的部分：

| 评审重点 | 具体问题 |
| --- | --- |
| 需求匹配 | 这真的解决了用户的问题吗？ |
| 边界 | 空数据、超大输入、并发、取消 |
| 可维护性 | 三个月后还能改吗？ |
| 一致性 | 与既有架构是否冲突？ |
| 隐含假设 | 代码里假设了什么前提？ |
| 依赖 | 新引入的库必要吗？有替代吗？ |

```js
// AI 常漏的三类边界
1. 并发与竞态（多个请求返回顺序不确定）
2. 资源清理（定时器、监听器、订阅）
3. 失败路径（网络失败、权限不足、数据缺失）
```

## 审查清单（可直接用）

```md
## AI 代码审查清单

### 正确性
- [ ] 是否有对输入不做校验的地方？
- [ ] 异步操作是否处理了失败与取消？
- [ ] 是否有隐含的时序假设（假设 A 一定先于 B）？

### 安全
- [ ] 是否拼接了用户输入到 HTML / SQL / 命令？
- [ ] 是否有硬编码的密钥或内部地址？
- [ ] 新增的依赖是否可信（维护活跃度、下载量、许可证）？

### 可维护
- [ ] 是否复制了现有工具函数（应复用）？
- [ ] 命名是否与项目约定一致？
- [ ] 复杂度是否可接受（嵌套层级、函数长度）？

### 测试
- [ ] 关键分支是否都有用例？
- [ ] 是否覆盖了边界（空、超长、并发、异常）？
- [ ] 测试是否验证行为而非实现细节？
```

## 用 AI 审查 AI（但要人把关）

```
第一遍：AI 审查（扫查常见问题，速度快）
第二遍：人审查（判断架构与业务一致性）
```

AI 审查的有效用法：

```md
请审查这个 PR，重点检查：
1. 异步操作的竞态与取消
2. 内存泄漏（定时器、监听器）
3. 边界条件（空值、超长、并发）
不要评论代码风格（已由 lint 覆盖）。
```

无效用法：让 AI 泛泛地"审查代码质量"，会得到一堆无用的风格建议。

## 度量效果

```
引入 AI 编码后，跟踪三个指标：
1. 缺陷密度（每千行 bug 数）是否上升
2. 代码审查时长是否变化
3. 回滚率 / 线上事故率是否变化
```

如果缺陷密度明显上升，说明"审查环节没跟上生成速度"，需要加强自动化而非减少 AI 使用。

::: warn 最危险的情况
```
AI 生成了 500 行 → 看着没问题 → 合并
→ 三个月后没人能解释这段逻辑
→ 出 bug 时只能重写
```
标准应该是：**合并的每一行，团队里至少有一个人能解释它为什么这样写**。
:::

::: interview 面试视角
"认真检查"是无效回答。能给出"自动化阻断 + 审查清单 + 聚焦边界"的可执行机制，并说明"如何度量效果"，才是高级回答。
:::
