## 核心原则

**重构的定义是"不改变外部行为的前提下改善内部结构"**。所以流程必须围绕"如何证明行为没变"来设计。

```
建安全网 → 小步重构 → 每步验证 → 持续交付
```

## 阶段一：建立安全网（最重要，占 40% 时间）

在没有测试的情况下用 AI 大改，是最高风险的做法。

```js
// 1. 用 AI 为关键路径补测试（先补"行为"，不补"实现"）
// AI 很擅长从现有代码反推测试用例

// 2. 建立端到端冒烟测试（覆盖核心用户流程）
// 3. 补充监控埋点，建立"重构前基线"
```

```js
// 基线示例：重构前后对比同一批操作的结果
const baseline = {
  ordersListRender: 'table with 20 rows',
  filterByStatus: 'filters correctly',
  exportCsv: 'downloads file with N rows'
}
```

::: warn 不要用 AI 生成的测试当作安全网
```
AI 根据现有代码生成的测试，往往"测试了现有实现"而非"测试了正确行为"
→ 如果现有代码有 bug，测试会把 bug 固化下来
```
正确做法：**先由人定义期望行为**（用业务语言），再让 AI 生成对应的测试代码。
:::

## 阶段二：识别重构单元

```
高价值 + 低风险 → 优先做
高价值 + 高风险 → 先补测试再做
低价值 → 不做
```

| 判断维度 | 信号 |
| --- | --- |
| 变更频率高 | git log 多次修改 |
| 缺陷密度高 | 该模块 bug 多 |
| 依赖复杂 | 循环依赖、深层嵌套 |
| 可测试性 | 纯函数容易、UI 难 |

## 阶段三：小步重构

```
一次只做一件事：
  第 1 步：提取工具函数（不改逻辑）
  第 2 步：拆分组件（不改逻辑）
  第 3 步：替换实现（改逻辑，但测试覆盖）
```

每一步都应：

1. 能独立合并（不要求"一次重构完"）
2. 有对应的测试
3. 可回滚

```bash
# 每步一个 PR，便于审查与回滚
git checkout -b refactor/extract-validators
```

## 阶段四：AI 的具体分工

| 任务 | AI 适合度 | 说明 |
| --- | --- | --- |
| 读懂旧代码并画依赖图 | ⭐⭐⭐⭐⭐ | 极强的场景 |
| 生成等价测试用例骨架 | ⭐⭐⭐⭐ | 需人定义期望 |
| 机械性替换（API 更名、语法升级） | ⭐⭐⭐⭐⭐ | 批量且可控 |
| 提取纯函数 | ⭐⭐⭐⭐ | 逻辑清晰时 |
| 拆分组件 | ⭐⭐⭐ | 需人判断边界 |
| 改架构 / 换技术栈 | ⭐⭐ | 需人主导 |
| 处理隐式副作用（全局变量、事件） | ⭐ | AI 容易漏 |

```md
<!-- 一个有效的提示词 -->
这是 legacy/order.js。请：
1. 列出所有对外暴露的函数与它们被谁调用
2. 标出所有副作用（修改全局、发请求、操作 DOM）
3. 不要修改代码，只输出分析
```

## 阶段五：验证

```js
// 三层验证
1. 单测：每个重构单元的行为一致
2. 回归：核心流程的 e2e
3. 线上：灰度 + 指标对比
```

```
灰度策略：
  5% 流量 → 观察 30 分钟错误率、性能指标
  → 25% → 50% → 100%
  任一步异常 → 立即回滚
```

## 常见失败模式

| 失败 | 原因 |
| --- | --- |
| 一个月后发现功能缺失 | 没补测试就大改 |
| 无法回滚 | 一次改动跨多个模块 |
| 重构后性能下降 | 没建立性能基线 |
| 团队不理解新代码 | AI 生成的抽象过于"聪明" |
| 越重构越乱 | 目标不明确，边改边加功能 |

::: tip 明确"不做什么"
重构最大的风险是范围蔓延。开始前写清楚：

```
本次重构只做：
- 拆分 order.js（1200 行 → 4 个模块）
- 提取校验逻辑为纯函数
不做：
- 不改接口协议
- 不升级框架版本
- 不改 UI
```
:::

::: interview 面试视角
能说清"安全网优先（占 40% 时间）"、"AI 生成的测试可能固化 bug"、"每步可独立回滚"，说明你主导过真实的重构而非只写过新代码。
:::
