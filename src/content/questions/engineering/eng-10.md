## 完整流程

```
接收 → 分级 → 复现 → 定位 → 修复 → 验证 → 复盘
```

## 1. 接收：结构化信息

很多反馈无法处理，是因为信息不全。应在反馈入口强制收集：

```js
// SDK 自动附加的环境信息
{
  user_id: 'u_123',
  app_version: '2.4.1',
  route: '/orders/987',
  ua: navigator.userAgent,
  screen: `${screen.width}x${screen.height}`,
  dpr: devicePixelRatio,
  network: navigator.connection?.effectiveType,
  timestamp: Date.now(),
  trace_id: getTraceId()   // 与后端日志关联
}
```

加上用户可填的"期望结果 / 实际操作步骤"，才有定位基础。

## 2. 分级

| 级别 | 标准 | 响应 |
| --- | --- | --- |
| P0 | 大面积不可用（白屏、无法登录） | 立即回滚 / 热修 |
| P1 | 核心功能受阻 | 当日修复 |
| P2 | 部分用户异常、有绕过方案 | 本周修复 |
| P3 | 体验问题、文案错误 | 排期处理 |

分级依据必须**可量化**：影响用户数、错误率、是否阻塞核心流程。

::: warn 只统计次数会误判优先级
```
一个用户刷新 100 次 → 错误次数 100
1000 个用户各遇到 1 次 → 错误次数 1000
```
必须同时看**影响用户数**，否则会优先处理"少数人的高频问题"而忽略"大面积问题"。
:::

## 3. 复现的三个层次

| 方式 | 说明 |
| --- | --- |
| 本地复现 | 用反馈中的版本、路由、设备信息 |
| 日志复现 | 查监控平台的堆栈与用户操作序列 |
| 录屏回放 | rrweb 等工具还原操作路径 |

```js
import { record } from 'rrweb'
record({
  emit(event) { buffer.push(event) },
  sampling: { mousemove: 50 }
})
```

::: warn 录屏涉及隐私
必须脱敏：屏蔽输入框内容、隐藏敏感区域（`rr-block` class）、告知用户并取得同意。
:::

## 4. 定位：从外到内

```
只影响特定版本？   → 对比上一版本
只影响特定设备？   → UA 分组
只影响特定路由？   → 代码分割边界
是接口问题？       → 网络 + 后端日志
是数据问题？       → 看用户的具体数据
```

工具组合：

| 工具 | 用途 |
| --- | --- |
| 监控平台 | 错误堆栈（source map 还原） |
| 接口日志 | 请求参数与响应 |
| 埋点分析 | 用户操作路径 |
| 录屏回放 | 视觉复现 |

## 5. 修复后必须验证三件事

1. **问题消失**（用同样条件复现）
2. **没有引入新问题**（回归测试）
3. **同类问题已排查**（是否还有相同代码模式）

```js
// 如果根因是"某个工具函数在某条件下崩溃"
// 应全局搜索同类调用，一起修掉
```

## 6. 复盘

```
现象 → 影响范围 → 时间线 → 根因 → 修复 → 改进项
```

改进项必须**可执行、有负责人、有截止时间**：

| 改进项 | 负责人 | 截止 |
| --- | --- | --- |
| 补充该场景的自动化测试 | 张三 | 本周 |
| 监控增加该错误的告警 | 李四 | 本周 |
| 重构该模块的错误处理 | 王五 | 下周 |

## 常见问题

| 问题 | 后果 |
| --- | --- |
| 反馈信息不全 | 无法复现，来回沟通数天 |
| 没有版本号 | 无法判断是否新引入 |
| 只统计次数不统计用户数 | 一个用户刷 100 次会误导优先级 |
| 修完不做同类排查 | 同类 bug 反复出现 |
| 复盘只写"已修复" | 没有改进，下次还会发生 |

::: interview 面试视角
能给出"结构化采集 → 量化分级 → 三层复现 → 同类排查 → 可执行改进项"的完整闭环，说明你处理过真实线上事故，而不只是"改了个 bug"。
:::
