## 输出顺序

```js
console.log('1')
setTimeout(() => {
  console.log('2')
  Promise.resolve().then(() => console.log('3'))
})
Promise.resolve().then(() => {
  console.log('4')
  setTimeout(() => console.log('5'))
})
console.log('6')
// 1 6 4 2 3 5
```

## 一轮循环的完整状态变化

| 阶段 | 调用栈 | 微任务队列 | 宏任务队列 |
| --- | --- | --- | --- |
| 执行同步代码 | `main()` | [] | [] |
| 同步结束 | 空 | [then→4] | [timer→2] |
| 清空微任务 | 空 | 执行 4，产生 [timer→5] | [timer→2] |
| 微任务清空后渲染检查 | 空 | [] | [timer→2, timer→5] |
| 取宏任务 2 | `timer2()` | 执行中产生 [then→3] | [timer→5] |
| 任务 2 结束 | 空 | [then→3] | [timer→5] |
| 清空微任务 | 空 | 执行 3 | [timer→5] |
| 取宏任务 5 | `timer5()` | [] | [] |

关键规则只有三条：

1. 一个宏任务执行完，**必须清空整个微任务队列**（执行中新产生的微任务也在本轮跑完）
2. 微任务清空后才可能进入渲染阶段
3. 渲染阶段才会执行 `requestAnimationFrame` 并可能绘制

## 队列归属

| 队列 | 来源 |
| --- | --- |
| 宏任务 | `setTimeout`/`setInterval`、I/O 回调、UI 事件、`MessageChannel`、`postMessage`、`setImmediate`(Node) |
| 微任务 | `Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`、`await` 续体 |
| 渲染 | `requestAnimationFrame` → 样式 → 布局 → 绘制 → 合成 |

::: warn 微任务可以饿死渲染
```js
function loop() { Promise.resolve().then(loop) }
loop() // 页面完全卡死，永远轮不到渲染
```
因为微任务队列永不空，浏览器拿不到绘制机会。这也是"不要用微任务做无限轮询"的原因。
:::

## 浏览器 vs Node.js

| 维度 | 浏览器 | Node.js |
| --- | --- | --- |
| 循环由谁驱动 | HTML 规范 + 渲染管线 | libuv |
| 阶段划分 | 单阶段（宏任务 → 微任务 → 渲染） | timers → pending → poll → check → close |
| 特有队列 | `requestAnimationFrame`、`requestIdleCallback` | `process.nextTick`、`setImmediate`、Promise 微任务 |
| 优先级细节 | 无独立高优队列 | `nextTick` 队列优先于 Promise 微任务 |

Node 中 `process.nextTick` 会在**当前操作结束后、Promise 微任务之前**执行：

```js
Promise.resolve().then(() => console.log('promise'))
process.nextTick(() => console.log('nextTick'))
// nextTick → promise
```

## 为什么要区分宏/微任务

微任务的设计目的是"在当前任务结束前完成必须的收尾"（如 Promise 链、副作用清理），保证状态一致；宏任务则用于"让出主线程，让浏览器有机会渲染或响应输入"。

::: interview 面试视角
只背"微任务先于宏任务"只能拿及格分。能画出队列表、说明"微任务可以饿死渲染"、并指出 Node 的 `nextTick` 差异，才是高级水平。
:::
