## 核心差异

| 维度 | ESM | CommonJS |
| --- | --- | --- |
| 语法 | `import` / `export` | `require` / `module.exports` |
| 加载时机 | 静态解析、编译时确定 | 运行时执行 |
| 加载方式 | 异步（浏览器）/ 同步（Node 的 ESM 加载器） | 同步 |
| 绑定 | **实时绑定**（live binding） | 值拷贝 |
| 顶层 await | 支持 | 不支持 |
| Tree Shaking | 支持 | 不支持 |
| 循环依赖 | 支持（但需注意 TDZ） | 支持（可能拿到未完成的 exports） |
| `this` | `undefined` | `module.exports` |

## 静态 vs 动态

ESM 的 `import` 必须写在顶层，路径必须是字符串字面量，**在代码执行前就确定了依赖图**。这正是 Tree Shaking 的前提。

CommonJS 的 `require` 可以在任意位置、用任意表达式：

```js
if (dev) require('./mock')       // 条件加载
require('./locale/' + lang)      // 动态路径
```

打包器无法静态分析，只能全量保留。

## 实时绑定

```js
// counter.mjs
export let count = 0
export function inc() { count++ }

// main.mjs
import { count, inc } from './counter.mjs'
console.log(count) // 0
inc()
console.log(count) // 1 —— 实时反映
```

CommonJS 是值拷贝：

```js
// counter.js
let count = 0
module.exports = { count, inc: () => count++ }

// main.js
const { count, inc } = require('./counter')
inc()
console.log(count) // 0 —— 拿到的是拷贝
```

## 互操作陷阱

### ESM 内导入 CJS

```js
import pkg from 'cjs-package'     // default 是 module.exports
import { named } from 'cjs-package' // Node 会尝试静态分析 named exports，可能失败
```

### CJS 内导入 ESM

```js
// Node 22+ 支持 require(esm)，但仍建议用动态 import
const mod = await import('esm-package')
```

### 双包问题（dual package hazard）

同一个包同时提供 ESM 与 CJS 入口，若两类消费者混用，会得到**两份不同的模块实例**，导致单例失效、`instanceof` 失败。解决方案是 `exports` 字段统一导出，且避免模块级可变状态。

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "types": "./dist/index.d.ts"
    }
  }
}
```

## 为什么 Tree Shaking 依赖 ESM

1. `import` 是静态语法，打包器能构建精确的依赖图
2. 导出是命名的，可以判断"是否被使用"
3. CJS 的 `module.exports = ...` 是动态赋值，无法静态判定

但 ESM 也不保证一定被摇掉：

```js
// 顶层副作用会让整个模块被保留
console.log('side effect')
export const a = 1

// 通过对象属性访问也无法静态裁剪
import * as m from './m.js'
m[key]
```

## 浏览器中的 ESM

```html
<script type="module" src="/main.js"></script>
```

三个特性：

- 默认 `defer` 行为（解析完成后执行，保证顺序）
- 严格模式
- 需要用绝对路径或相对路径（裸模块名需 import map 或构建工具）
