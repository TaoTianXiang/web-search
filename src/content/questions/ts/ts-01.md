## 能力对照

| 能力 | interface | type |
| --- | --- | --- |
| 描述对象 | ✅ | ✅ |
| 同名声明合并 | ✅ | ❌ |
| 联合类型 | ❌ | ✅ |
| 交叉类型 | 通过 extends | ✅ `&` |
| 条件类型 | ❌ | ✅ |
| 映射类型 | ❌ | ✅ |
| 元组 / 字面量类型 | ❌ | ✅ |
| 索引签名 | ✅ | ✅ |
| 扩展已有类型 | `extends` | `&` |
| 实现类 | `implements` | `implements` |
| 编译性能 | 更快（接口检查便宜） | 复杂类型可能变慢 |
| 报错可读性 | 更友好（显示接口名） | 复杂变换时可读性差 |

## 声明合并

```ts
interface Window { __APP_CONFIG__: AppConfig }
interface Window { __THEME__: string }
// 两者合并为一个

type T = { a: string }
// type T = { b: number }   // ❌ 重复声明报错
```

用途：扩充第三方类型、为全局对象补充字段。

```ts
declare module 'vue' {
  interface ComponentCustomProperties {
    $http: HttpClient
  }
}
```

## type 独有的能力

```ts
// 1. 联合
type Status = 'idle' | 'loading' | 'success' | 'error'

// 2. 条件类型
type Unwrap<T> = T extends Promise<infer U> ? U : T

// 3. 映射类型
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] }

// 4. 函数类型 / 元组
type Handler = (e: Event) => void
type Pair = [number, string]

// 5. 字面量
type Level = 1 | 2 | 3
```

interface 无法表达上面任何一种。

## 性能差异的真实影响

```ts
// interface：编译器可以快速判断"是否兼容"，因为结构固定
interface User { id: string; name: string }

// type 经过多层变换：每次检查都要展开
type DeepPartial<T> = { [K in keyof T]?: DeepPartial<T[K]> }
type A = DeepPartial<DeepPartial<DeepPartial<HugeType>>>
```

在大型项目里，深层 type 变换会显著拖慢 tsc。这也是"对外 API 用 interface"的一个现实理由。

## 推荐规范

```ts
// ✅ 对外的对象契约用 interface
export interface User { id: string; name: string; role: Role }

// ✅ 联合、工具类型、函数签名用 type
export type Role = 'admin' | 'editor' | 'viewer'
export type UserWithRole = User & { roleLabel: string }

// ✅ 组件 Props 通常用 interface（便于扩展与报错可读）
export interface ButtonProps { size?: 'sm' | 'md'; onClick?: () => void }
```

判断标准：

| 问题 | 选择 |
| --- | --- |
| 是对象形状，且可能被使用方扩展？ | interface |
| 是联合 / 元组 / 条件 / 映射？ | type |
| 需要同名合并（如扩充全局）？ | interface |
| 团队偏好统一？ | 统一一种也可，但要写进规范 |

## 常见误区

```ts
// ❌ 用 interface 表达联合
interface Status { }   // 做不到

// ❌ 用 type 表达需要合并的类型
type Config = { a: string }
type Config = { b: string }   // 报错，若需合并应使用 interface

// ❌ 混用导致理解成本
// 同一文件里一半用 interface 一半用 type，且没有明确规则
```

::: tip 一个实用结论
两者能力交集很大，**选哪个都能写出好代码**。真正重要的是：团队内统一、并且理解"什么时候某种方式做不到"。规范是为了减少争论，不是为了证明谁更好。
:::

::: interview 面试视角
能说清"声明合并"与"编译性能"这两个差异，并给出"对外契约用 interface、组合变换用 type"的判断标准，比只说"type 更灵活"有价值。
:::
