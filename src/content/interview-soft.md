技术能力决定你能不能做，表达能力决定别人知不知道你能做。面试中的"讲项目"环节，本质是在有限时间内证明你的**判断力**。

## STAR 的局限与改进

STAR（Situation、Task、Action、Result）是基础，但它不强调"为什么"。

改进版：**SCQA-R**

```
S  Situation  背景与规模
C  Constraint 约束条件（时间、人力、技术债）
Q  Question   要解决的核心问题
A  Alternatives 备选方案及对比
R  Result     结果与度量，以及反思
```

关键差别：加上 **C（约束）** 和 **A（备选）**，面试官才能看到你的决策过程。

## 一个完整的讲述示例

::: tip 示例：表格性能优化
**背景**：B 端风控后台，核心列表单页渲染 5 万行，运营每天要筛查 3 小时以上，投诉集中在滚动卡顿与筛选慢。

**约束**：
- 后端分页协议刚上线，不能改
- 需要兼容客户已配置的 30 多套列方案
- 排期两周（含测试）

**备选方案**：
1. 服务端筛选 + 分页：改动小，但客户习惯一次性看全量数据，体验下降明显
2. 虚拟滚动：一次性渲染 5 万行中可见的 20 行，滚动流畅，但要处理动态行高与列冻结
3. 虚拟滚动 + Web Worker 预处理：把排序/分组放到 Worker，进一步减少主线程压力

**取舍**：选 2。放弃动态行高（统一 40px），换来实现复杂度与稳定性的平衡；把方案 3 作为后续优化项。

**落地**：
- `vue-virtual-scroller` 只渲染可见行
- 列宽用 `ResizeObserver` 动态计算
- 筛选逻辑抽成纯函数，用 `requestIdleCallback` 预计算
- 缓存上次滚动位置与筛选条件

**结果**：
- 首屏渲染 1.2s → 180ms
- 滚动帧率 30fps → 58fps
- 运营单次筛查时长 3h → 1.2h
- 相关投诉下降 70%

**反思**：如果重来，我会先埋点确认"卡顿主要发生在滚动还是筛选"，避免一开始就在两个方向上并行投入。
:::

### 为什么这个例子有效

| 要素 | 作用 |
| --- | --- |
| 具体数字 | 5 万行、1.2s、70% —— 可验证 |
| 明确约束 | 不能改协议、两周排期 —— 真实 |
| 备选对比 | 三个方案，说清为什么淘汰两个 |
| 主动暴露权衡 | 放弃动态行高 —— 显示你懂取舍 |
| 反思 | 承认可以做得更好 —— 显示成长性 |

## 常见追问与准备

### 1. "这个方案的边界在哪？"

准备答案的框架：**什么情况下会失效**。

> 统一 40px 行高在多行文本场景下会截断内容，我们用 tooltip 补足。如果业务出现大量富文本行，需要改成动态行高 + 二分查找，性能会下降约 30%。

### 2. "如果数据量再涨 10 倍呢？"

> 50 万行时虚拟滚动仍可用，但筛选会变慢。届时需要把筛选下沉到服务端，或者引入 IndexedDB 做本地倒排索引。当前架构预留了这个替换点：筛选逻辑是纯函数，可以从主线程移到 Worker 或服务端。

### 3. "你怎么验证优化真的生效了？"

> 三层验证：
> 1. 实验室：Lighthouse + Performance 面板对比关键帧
> 2. 线上：RUM 采集帧率与交互延迟的 p75
> 3. 业务：运营的单次筛查时长埋点

### 4. "团队里其他人怎么复用这个方案？"

> 抽成了 `<VirtualTable>` 组件，列配置驱动，已在 4 个页面接入。文档里写明了"什么场景不适合用"。

::: warn 最容易翻车的追问
"这个方案是你主导的吗？" —— 如果实际是别人做的，要诚实说明你负责的部分。面试官经常通过追问细节来验证真实性（比如具体某个 API 的名字、某个 bug 怎么修的）。
:::

## 系统设计题的答题框架

系统设计题（设计一个前端 SDK / 组件库 / 中后台框架）不要直接讲技术选型。

### 第 1 步：澄清需求（30%）

```
- 使用场景是什么？（B 端 / C 端 / 内部工具）
- 规模量级？（QPS、数据量、并发用户）
- 非功能要求？（首屏时间、可用性、可维护性）
- 团队情况？（人数、技术栈、维护周期）
- 交付时间？
```

不问清楚就画架构，是最常见的失分点。

### 第 2 步：划分边界（20%）

```
核心能力（必须做）
扩展能力（可插拔）
不做（明确排除）
```

明确"不做什么"比"做什么"更能体现判断力。

### 第 3 步：方案设计（30%）

```
- 数据流：状态从哪来、到哪去
- 分层：哪些是基础能力、哪些是业务封装
- 关键接口设计
- 错误处理与降级
```

### 第 4 步：验证与风险（20%）

```
- 如何度量成功
- 最可能失败的点
- 灰度与回滚方案
- 迁移路径（如果是改造存量）
```

## 反问环节：你也在面试公司

好的反问能显著提升评价。避免问"公司文化怎么样"这种无法回答的问题。

### 推荐问法

| 方向 | 问题 |
| --- | --- |
| 技术 | 团队目前最大的技术债是什么？有没有在还的计划？ |
| 流程 | 从需求到上线要走哪些环节？平均周期多久？ |
| 质量 | 线上出问题怎么定位？有没有接入监控与告警？ |
| 成长 | 这个岗位未来一年最重要的三件事是什么？ |
| 协作 | 前端与后端、设计的协作方式是怎么样的？ |

### 避免问法

- "加班多吗？"（可以问，但换个方式："团队一般什么时候最忙？"）
- "我能学到东西吗？"（这是你的责任，不是公司的）
- "什么时候能给我答复？"（留给 HR）

## 薪资沟通

### 基本策略

1. **先让对方给范围**："这个岗位的预算区间是多少？"
2. **报区间不报单点**：给出期望区间的下限略高于你的底线
3. **用总包比较**：base、奖金、股票、补贴要分开看
4. **不要虚报现薪**：背调很容易查出来

### 谈崩的常见原因

- 过早暴露底线
- 拿不到 offer 就谈薪
- 只谈钱不谈价值（"我值这个价"要说清价值锚点）

## 时间分配

一场 60 分钟的技术面，理想分布：

```
自我介绍        3-5 min
项目深挖        20-25 min
技术问题        20-25 min
反问            5 min
```

### 自我介绍模板

```
1. 一句话现状：X 年经验，目前在 Y 公司做 Z 方向
2. 一个代表性成果：最近做的项目 + 量化结果
3. 与岗位的匹配点：为什么我对这个位置感兴趣
```

控制在 90 秒内。太长会让面试官失去耐心。

## 常见失分点清单

| 失分点 | 改进 |
| --- | --- |
| 只讲技术，不讲业务价值 | 每段技术描述后加"这带来了什么" |
| 说"我们团队做了" | 明确"我负责哪部分" |
| 没有数字 | 提前准备 5 个关键指标 |
| 报答案不报过程 | 讲"我一开始以为…后来发现…" |
| 遇到不会的问题硬编 | 说"这块我不熟，但我会从 X 角度切入" |
| 反问说"没问题" | 准备 3 个问题，至少问 1 个 |

::: interview 面试视角
面试官评估的从来不是"你懂多少"，而是**"你是否值得信任地把事情交给你"**。清晰表达取舍、诚实承认边界、量化结果 —— 这三点构建的正是这种信任。
:::

## 长期准备建议

1. **维护一份项目笔记**：每个项目的背景、约束、方案、结果、反思，随时更新
2. **每季度复盘一次**：哪些判断对了，哪些错了，为什么
3. **练习口述**：对着录音讲 5 分钟，回听会发现大量冗余
4. **准备三个深度案例**：一个技术深度、一个业务复杂度、一个协作推动
5. **了解目标公司**：技术博客、开源项目、产品形态

::: tip 最后一点
面试是双向选择。如果一家公司只关心"你能不能背出 diff 算法"，而不关心"你怎么判断该不该用某个方案"，那可能不是适合长期发展的地方。
:::
